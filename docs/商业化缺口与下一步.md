# 商业化缺口与下一步

> **性质**：产品/工程待办清单（下一步要做的事），不是已完成设计。  
> **评估日期**：2026-07-11  
> **成熟度**：约 3.5 / 10 — 可支撑邀请制公开演示或单客户代运维；尚不可作为可售卖 SaaS / 闭源商业软件直接售卖。  
> **相关**： [可行性评估.md](./可行性评估.md)（HTTP 服务化）、[架构与改造方案.md](./架构与改造方案.md)、`docs/superpowers/specs/2026-06-20-public-deploy-auth-design.md`（认证设计，明确未做组织权限/billing）

## 1. 结论（先定产品形态）

当前代码是 **强公共部署 MVP**：HTTP 只读 UI、混合搜索、Rust Chat SSE、Cookie 认证、日聊天配额、SMTP 重置、部署/备份 runbook。

| 形态 | 是否推荐近期 | 说明 |
|------|--------------|------|
| **单租户托管**（一客户一实例） | ✅ 首选 | 最贴近现有架构（一 wiki 树 + 一 SQLite auth DB） |
| **自托管 + 支持服务** | ✅ 可选 | 在 GPL 下卖支持/代运维/打包；勿默认卖闭源 |
| **真·多租户 SaaS** | ❌ 延后 | 缺 ACL、计费、隔离、滥用防控，接近再做一层产品 |
| **闭源 License 售卖** | ⚠️ 先解许可 | 上游 + 本仓 GPL-3.0；未谈妥双许可前不要按闭源包装 |

**差异化相对上游桌面版**：可托管、多用户 Lite、配额、运维脚本、HTTP 搜索/Chat — 不是另一套私有核心。

## 2. 现状能力速览

### 已有（可当内测底座）

- Headless HTTP + 混合搜索（向量侧可降级）+ Rust 流式 Chat
- 邮箱注册/登录/登出/会话（argon2、HttpOnly Cookie）
- 日聊天配额（Cookie 用户）、会话历史
- SMTP 密码重置、`DISABLE_REGISTRATION`、健康检查 / 优雅关闭
- ECS 部署与备份文档、Prometheus `/metrics`

### 半成品（看起来像商业，实际不够）

- 「邀请制」= 关注册；无邀请码、无运营建用户 API
- `is_admin` 仅注册时按邮箱标记；**无管理路由/UI**
- 配额不覆盖 Bearer 神钥；无套餐/座位/$ 计量
- Docker 文档偏旧；「多用户」但**无项目 ACL**
- Landing 有登录页，无 ToS/隐私/营销合规页

### 商业缺失

- Billing / Stripe / 订阅权益
- 组织/多租户、用户↔项目权限
- 自助建库与 Web 上传 ingest
- 管理后台、账号导出/注销、审计日志
- HA、客户级一键安装包、商业许可策略落地

## 4. 下一步要做的事（优先级）

> 下列条目是 **明确待办**。实施前需选定产品形态（§1）；默认按「单租户托管 / 邀请制付费内测」推进。

### P0 — 阻塞「能收费 / 能公开放客」

| ID | 事项 | 验收标准 |
|----|------|----------|
| P0-1 | **定许可路径** | 书面结论三选一：只卖托管（ASP）/ 开源+卖支持 / 与上游谈双许可；据此定分发与定价文案 |
| P0-2 | **用户↔项目 ACL** | 配置或表：用户只能 list/访问被授权的 `project_id`；未授权返回 403；冒烟测试覆盖 |
| P0-3 | **收敛 Bearer 神钥** | 文档标明仅运维；终端用户走 Cookie；配额对会烧 LLM 的路径生效（或独立 per-user API key + 配额） |
| P0-4 | **最小计费/权益** | 至少：付费后可开通账号 + 可配置日限额；可先 Stripe 收款 + 人工开通，再接 webhook |

### P1 — 付费内测最小集

| ID | 事项 | 验收标准 |
|----|------|----------|
| P1-1 | **真实邀请/开通** | 邀请码 **或** admin 创建用户 API；`is_admin` 真正可用 |
| P1-2 | **ToS + 隐私页** | Landing/登录页可链到；存放于静态目录 |
| P1-3 | **账号导出 + 注销** | 用户可导出对话 JSON；可删除账号及级联数据 |
| P1-4 | **安全加固** | CORS 白名单；`/metrics` 鉴权或仅内网；评估去掉浏览器 `?token=` |
| P1-5 | **用量可见** | Lite/`/auth/me` 展示 `usage.used/limit` |

### P2 — 正式运维与增长（内测后）

| ID | 事项 | 验收标准 |
|----|------|----------|
| P2-1 | **管理后台 MVP** | 列用户、改限额、禁用账号、开关注册 |
| P2-2 | **邮箱验证** | 注册后验证才可 chat（或仅邀请用户跳过） |
| P2-3 | **自助/引导 ingest** | Web 上传或受控触发；或明确「仅代运维客户」不卖自助 |
| P2-4 | **备份产品化** | cron 热备 + 一年一次恢复演练记录 |
| P2-5 | **Docker/安装包刷新** | compose 含 auth DB、landing、`REQUIRE_LOGIN`；文档与「Chat 纯 Rust」一致 |
| P2-6 | **HA / 多实例** | 企业单再做；内测不阻塞 |

### 明确延后（本阶段不做）

- 真多租户共享 DB、组织/团队 RBAC 全家桶  
- SSO / SAML、企业审计 SIEM  
- 完整 Web 写路径替代 CLI ingest（除非选定纯 SaaS 自助）

## 5. 建议节奏（4–6 周付费内测）

按 **单租户托管或邀请制自托管**，不做完整多租户 SaaS。

| 周次 | 聚焦 | 对应待办 |
|------|------|----------|
| 第 1 周 | 许可结论 + ToS/隐私 + 关注册运维手册 | P0-1, P1-2, P1-1（手册或最小 API） |
| 第 1–2 周 | CORS / metrics / Bearer 边界 | P0-3, P1-4 |
| 第 2 周 | 项目 ACL（配置白名单即可起步） | P0-2 |
| 第 2–3 周 | 配额产品化 + 用量展示 | P1-5, P0-4（人工开通） |
| 第 3–4 周 | Admin MVP + 导出/注销 | P2-1, P1-3 |
| 第 4–5 周 | 备份演练 + 安装文档/Docker | P2-4, P2-5 |
| 第 5–6 周 | Stripe 半自动 → webhook 改限额 | P0-4 自动化 |
