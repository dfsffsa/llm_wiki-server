# 电子书批量入库 — 经验教训(2026-08-06 回顾)

> 背景:8 本育儿电子书 → 切分 1256 块 → LLM 语义检查 → 并行 ingest 1256 源文件 → eval。
> 全程使用 subagent-driven-development(每任务 implementer + 规格评审 + 质量评审)。
> 本文回顾全程,提炼**可复用的教训**。按严重度排序,每条附"教训"与"做法"。

---

## 一、过程与协作(最值得反思)

### L1. Worktree 隔离失效:子代理在主 checkout 的 main 分支直接提交
- **发生了什么**:用户选了"新建 worktree 隔离",但派发子代理时我给了它们**主 checkout 的绝对路径**(`/home/ab/overseas-github/llm_wiki-server`),而非 worktree 路径。结果全部 11 个任务的工作、10+ commits 全落在 `main` 分支上,worktree `feat+ebook-ingestion` 是空的,白建了。
- **代价**:worktree 隔离目的落空;交接文档一度写错位置,第二天才发现工作全在 main。
- **教训**:**派发子代理时必须显式给出目标 worktree 的绝对路径,并在任务早期验证子代理实际在哪个目录操作**(`pwd`/`git branch`),而不是到交接时才确认。

### L2. 计划的测试代码本身可能就有 bug,实现者不该为迁就它改实现
- **发生了什么**:计划里的 `test_cuts_at_paragraph_boundary` 用 `"".join(chunks)` 拼接块,抹掉了段落边界,导致**正确的实现**也会断言失败。实现者(haiku)为了过测试,把 `subsplit` 改成给后续块加 `"\n\n"` 前缀(方向错误、污染输出)。spec reviewer 抓出根因:是**测试 bug**,不是实现 bug。
- **教训**:(1) plan 里的代码要当真实代码一样审查;(2) 实现遇到"测试不过但实现看起来对"时,**先怀疑测试**,别改实现去迁就;(3) 两阶段评审(尤其 spec reviewer)确实拦住了这类会放大成批处理灾难的缺陷。

### L3. 数据量假设严重低估:计划 300–600 块,实际 1256
- **发生了什么**:计划估 8 本共 300–600 块,实际 **1256 块**。《定本育儿百科》是 651 个编号词条组织的参考书,单本就 684 块。成本(LLM 检查 ~70min、ingest ~10h)翻 2–4 倍。
- **教训**:**对不确定的数据量,先抽一本真实书实测切分,别按直觉估**。成本敏感决策(全量检查 vs 抽样)应在拿到真实量级后再让用户拍板。

## 二、工程实现

### L4. LLM 输出解析必须健壮:拒绝/非 JSON 崩整批
- **发生了什么**:LLM 输出三类问题——结尾多余引号、JSON 值里混 `if/else` 表达式、内容政策拒绝(如"自慰"章节回复"无法给到相关内容")。`parse_json_response` 抛 ValueError,`check_chunk` 不接,直接崩掉整本书的检查。
- **修复**:平衡大括号提取 + if/else 清理(commit `8360cac`);`check_chunk` 逐块 try/except,记 `error` verdict 继续跑(commit `dd228c2`)。
- **教训**:**LLM 管线要把"解析失败/拒绝"当预期情况处理**,逐块容错,绝不因为单个坏输出崩整批。

### L5. 长任务必须增量持久化进度
- **发生了什么**:`save_cache` 只在整个 chunk 循环结束后写盘。中途崩(LLM 错误/模型故障/超时)丢**全部**进度,重跑很贵。
- **修复**:`run_check` 每块增量写缓存(commit `f99031f`)。
- **教训**:任何长时批处理,**进度要能断点续跑**,以块/文件为单位持久化。

### L6. bash 路径循环绝不能用 `${arr}` 拆词(空格 bug)
- **发生了什么**:并行 ingest 驱动用 `for f in ${groups[$i]}` 迭代文件路径。西尔斯(`CHAPTER 17` 半角空格)、崔玉涛自然、第一次当奶爸的**文件名含半角空格**,被按空格拆碎 → **765 次 FAILED,354 个文件静默没入库**,而 `==> all workers done` 还照常打印。我在脚本注释里写了"路径无空格"——错误的假设。
- **修复**:改为逐行文件列表 + `while IFS= read -r f`(commit `0f956d7`)。
- **教训**:(1) bash 里任何含路径的循环都用 `read -r` 逐行读,别裸拆词;(2) **别假设文件名无空格**,中文转义过的章节标题(CHAPTER N)天然带空格;(3) 驱动脚本要自带"预期文件数 vs 实际成功数"校验,而不是让"done"当完成信号。

### L7. `pkill -f` 会匹配到自己的命令行
- **发生了什么**:`pkill -f "tsx cli.mjs"` 匹配到了执行它的 shell 自己的命令行 → 把自己杀了(exit 144)。
- **教训**:`pkill -f` 用方括号防自匹配:`pkill -9 -f "[t]sx cli.mjs"`。同理 `[l]lm-wiki`。

### L8. 杀进程要连子树一起,杀完验证零残留
- **发生了什么**:`TaskStop` 杀了 ingest 主脚本,但它的 node/tsx **孙进程成了孤儿还在继续 ingest**,和新 run 双跑(17 个 tsx 进程)。
- **教训**:杀进程树后必须 `pgrep` 验证**零残留**,再重启。

### L9. 长时任务必须脱离会话
- **发生了什么**:`run_in_background` 的 bash 任务会话绑定,会话结束就死。10 小时 ingest 用会话绑定任务有被杀风险。
- **做法**:`setsid nohup env ... bash script > log 2>&1 &` 完全脱离,可跨会话存活、可续跑。

## 三、监控与运维

### L10. 监控要查对的日志 —— 本次最大的盲区
- **发生了什么**:为 ingest 建了每 15 分钟的 cron 监控循环,但异常 grep 查的是 **worker 日志**(`ingest-w*.log`,只含 ingest 过程输出),而 ok/FAILED 标记在**主日志**(`ingest-parallel-fixed.log`)。结果 **765 次 FAILED 全程没被发现**,直到 run 结束、`pending=354` 才暴露。
- **教训**:**监控脚本先拿已知正/负样本验证口径**(先 grep 一个已知 FAILED 看能不能抓到)。调度者要理解"状态标记在哪一层"。

### L11. 监控关键词要防误报
- **发生了什么**:裸 `429` 匹配到《定本》词条编号(文件名 `1115-429.防止事故.md`),虚惊一场。
- **教训**:用精确模式(`rate_limit_error` / `Too Many Requests` / `Analysis failed`),别用裸数字。

### L12. 批处理前检查所有 LLM 端点配额
- **发生了什么**:ingest 用的 **MiniMax-M2.7 配额耗尽**(429,"已达到 Token Plan 用量上限"),而检查用的 **Tencent tokenhub 正常**。不同步骤用不同端点,配额各自独立。
- **教训**:批量前先对**每个要用的端点**测一次真实调用;准备好 fallback 配置(本次切到 `deepseek-v4-flash-202605`)。

## 四、工具与数据语义

### L13. 工具的 arg 语义要读代码,别信 help 文本
- **发生了什么**:`rag_eval.py --project` 的 help 写"项目路径",实际**按项目名匹配** `/api/v1/projects` 列表;传完整路径 → 匹配失败 → 回退到列表第一个项目(**CivilCareer**)→ 搜到 `bgs-*` 内容 → **0 命中**,误导我以为检索坏了。
- **同样**:`run_eval.sh` 内置的 rag_eval 不带 API token,对 `authRequired:true` 的 server 直接 401。
- **教训**:eval/工具类脚本,传参前看它**实际怎么解析**(grep 代码),别只信 help;需要 auth 的 eval 要显式 `--token`。

### L14. 测试用例生成有覆盖偏置
- **发生了什么**:`generate_test_cases.py` 按目录序(`ls`)处理源文件,撞到 target_count(60)就停 → **60 条用例全来自排最前的《养育女孩》**,其余 7 本零覆盖。
- **教训**:多书/多目录场景,要么按书生成再合并,要么生成器支持随机采样;别指望一次跑出均衡覆盖。

### L15. 指标要懂它实际测什么
- **发生了什么**:eval 的 Chat"准确率 0/60"——v2 用例**缺 `expected_answers` 字段**,`answer_match` 对空列表恒 0。这不是回答质量差,是评分伪象。
- **教训**:报指标前先确认它怎么算的、依赖什么字段;测不出就说测不出,别让 0 被误读。

### L16. 中文电子书章节格式千差万别
- **发生了什么**:8 本书 6 种正文标题格式:`第N章　`(全角空格)/ `N.` / `NN ` / `CHAPTER N` / `第一章 ` / `第一章`(独立行)。默认正则只对 2 本有效,6 本需 per-book `--heading-re`。
- **教训**:切分工具必须支持 per-book 正则覆盖,**并逐本抽查验证**章节数(本次靠 spec reviewer 抽查 5 个样本确认定本 684 块合理)。

### L17. embedding 禁用时,如实说"测的是关键词检索"
- **发生了什么**:server.local.json `embeddingConfig.enabled=false`(无 DashScope key),检索退化为纯关键词(hybrid 降级设计)。新书 source_hit@10 仅 41.7%。
- **教训**:检索指标要注明模式(关键词 vs 混合);要测向量检索就得先配置 embedding 并 `reindex --vectors`。

## 五、值得坚持的做法

- **文档随进度更新**:handoff 文档(progress.md)每天更新,第二天续跑靠它快速恢复上下文;交接时连"工作产物在 main 不在 worktree"这种纠错都写进去。
- **两阶段评审**(spec + quality)虽有成本,但确实拦住了 off-by-one、YAML 转义、buggy 测试等会在批处理放大成灾难的问题。
- **对数字诚实**:检索 41.7% 就报 41.7%(并注明关键词模式);Chat 0% 说明是评分伪象,不掩盖。

---

## 一句话总结

> 大规模 LLM 批处理管线,成败在**容错**(解析、进度、路径、监控四层都要容错)和**数据真实**(先实测量级、校验 arg 语义、确认监控口径);而 subagent 编排的价值在于把"计划的 bug""实现的方向错"在放大前拦下来。
