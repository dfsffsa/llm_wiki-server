# 知识库 AI 问答产品 \- 竞品前端交互设计调研报告

## 一、竞品逐个分析

### A 组：开源且活跃

#### 1\. Onyx（原 Danswer）

**一句话定位**：企业级开源自托管知识搜索与聊天平台，连接内部工具文档，提供带来源引用的可信回答。

**界面布局描述**：

- 左侧边栏：项目 / 知识库列表 \+ 数据源连接器管理

- 中央区域：聊天主界面，消息气泡式对话

- 顶部输入栏：集成文件 / URL 上传、动作选择器（Document Search / Deep Research / Web Search）、模型选择下拉

- 整体风格：简洁现代，浅色主题，以对话为核心

**3 个值得借鉴的设计点**：

1. **输入栏多功能集成**：将模式切换（搜索 / 聊天 / 深度研究）、文件上传、模型选择都整合在输入框周边，减少页面跳转，纯 JS 即可实现

2. **渐进式来源展示**：引用徽章内嵌在回答中，点击展开详情，不干扰阅读主线

3. **Chat/Search 双模式切换**：同一界面下切换问答模式和搜索模式，后端可复用检索逻辑，前端只需切换展示形态

---

#### 2\. RagFlow

**一句话定位**：深度文档理解的开源 RAG 引擎，主打精细的文档结构解析与可追溯引用。

**界面布局描述**：

- 左侧：会话历史侧边栏，按时间排列对话

- 右侧主区：聊天界面，用户消息右对齐、AI 消息左对齐

- 引用系统：回答中角标 \[1\]\[2\] 标注，悬浮弹出预览浮卡

- 支持深色 / 浅色主题切换

- 独立的知识库管理页面，展示文档解析进度和分块预览

**3 个值得借鉴的设计点**：

1. **角标引用 \+ 悬浮预览 \+ 上下文抽屉三层设计**：hover 看片段、点开放全文、抽屉看上下文，验证成本极低

2. **分块可视化界面**：让用户直观看到文档被切成了哪些片段、哪些被检索到，建立对 RAG 机制的信任

3. **双主题原生支持**：深色模式对长时阅读友好，纯 CSS 变量即可实现

---

#### 3\. AnythingLLM

**一句话定位**：一体化桌面 AI 应用，以工作区（Workspace）为核心组织文档和对话，支持完全本地离线运行。

**界面布局描述**：

- 左侧导航栏：工作区列表、系统设置入口

- 中央：聊天主区域，工作区切换后对话和文档同步切换

- 右侧：可展开的设置面板（模型参数、温度等）

- 工作区概念：类似 "项目文件夹"，每个工作区有独立的文档集合和对话历史

- 桌面端原生应用体验，也支持 Web 端自部署

**3 个值得借鉴的设计点**：

1. **Workspace 容器化设计**：将文档和对话绑定在同一工作区，切换工作区即切换上下文，符合 "先有文档再问答" 的使用逻辑

2. **极简三栏布局**：导航 \+ 聊天 \+ 设置，结构清晰，纯静态页面容易实现

3. **零门槛 Onboarding**：启动即进入，无需注册，直接选择模型创建工作区，对小团队 / 个人用户友好

### B 组：商业但设计优秀

#### 4\. Google NotebookLM

**一句话定位**：AI 原生研究笔记工具，三栏式布局将源文件、对话、生成内容整合在同一视图。

**界面布局描述**：

- **三栏弹性布局**：

    - 左栏 Sources：源文件列表，可收缩为图标导航 rail

    - 中栏 Chat：对话聊天区，回答标注来源页码

    - 右栏 Studio：音频概览、思维导图、学习指南等生成内容

- 各栏宽度可拖拽调整，根据任务侧重灵活分配空间

- 整体 Google 设计语言，圆角卡片、大量留白

**3 个值得借鉴的设计点**：

1. **三栏可伸缩信息架构**：Sources\-Chat\-Studio 对应知识库问答的三大核心要素（输入 \- 交互 \- 输出），窄屏时左右栏可收起，适配性强

2. **来源标注精确到页码**："来自 XX 文档第 3 页" 比简单链接更有信任感，且技术实现简单

3. **同屏多任务并行**：边看原文边聊天边整理笔记，减少上下文切换，提升深度研究效率

#### 5\. Perplexity

**一句话定位**：AI 原生搜索引擎，搜索即问答，以简洁的单栏对话 \+ 透明来源展示为核心。

**界面布局描述**：

- 首页：居中大搜索框，类 ChatGPT 的极简设计

- 回答页：问题在上、回答在中、来源卡片列表在底部

- 左侧边栏：历史记录 \+ Spaces（空间）列表

- 深色主题为主，视觉聚焦在内容本身

- 回答中内联来源角标，底部有完整来源卡片

- Spaces 功能：按主题组织研究线程和文档，类似项目文件夹

**3 个值得借鉴的设计点**：

1. **搜索 / 问答统一入口**：一个输入框同时承担搜索和对话，减少用户认知负担，符合 "先检索再生成" 的 RAG 本质

2. **来源卡片底部聚合**：回答正文保持干净，所有来源在底部以卡片形式展示，包含标题、摘要、链接，兼顾可读性和可验证性

3. **Spaces 主题化组织**：将相关对话、上传文件聚合在一个 Space 中，比平铺的会话列表更有结构感，适合持续研究场景

#### 6\. Notion AI Q\&A

**一句话定位**：内嵌在 Notion 知识库中的问答助手，无独立界面，以浮层形式融入现有工作流。

**界面布局描述**：

- 入口：右下角闪烁图标 / 全局搜索框 / 键盘快捷键唤起

- 形态：侧边滑出面板或悬浮弹窗，不离开当前页面

- 回答下方列出引用的 Notion 页面链接

- 支持限定搜索范围（整个工作区 / 指定页面树）

- 完全融入 Notion 现有 UI，无割裂感

**3 个值得借鉴的设计点**：

1. **无处不在的入口设计**：搜索栏、右下角按钮、快捷键，多种方式触达，降低使用门槛

2. **上下文感知问答**：在哪个页面提问就优先搜该页面的内容，问答与浏览无缝衔接

3. **范围限定器**：让用户选择 "问整个库还是问当前文件夹"，既精准又灵活

## 二、横向对比分析

### a\) 初始页面设计对比

|产品|第一眼看到什么|选知识库的时机|设计理念|
|---|---|---|---|
|Onyx|聊天输入框 \+ 左侧项目列表|进入前已选好，侧边栏切换|项目为中心，对话为主界面|
|RagFlow|左侧会话列表 \+ 空白聊天区|创建会话时关联知识库|会话为中心，知识库隐式绑定|
|AnythingLLM|工作区列表 \+ 新建按钮|先选 / 建工作区，再进入聊天|Workspace 容器化，文档对话绑定|
|NotebookLM|三栏：Sources \+ Chat \+ Studio|Notebook 即知识库，打开即选定|笔记本隐喻，三要素同屏|
|Perplexity|居中大搜索框|进入 Space 后限定范围|搜索优先，Space 是可选增强|
|Notion AI|无独立页面，浮层唤起|当前页面 / 可选范围|嵌入式，不打断工作流|

**洞察**：对于 "先有文档再问答" 的场景，**Workspace/Notebook 模式更优**—— 用户先创建 / 选择一个知识容器，再在里面对话，心智模型清晰。直接丢进空聊天框会让用户困惑 "我在跟哪个知识库对话"。

### b\) 思考 / 推理展示对比

|产品|推理展示方式|默认状态|交互方式|
|---|---|---|---|
|Perplexity|搜索步骤进度条（"正在搜索 X\.\.\."）|展示|自动滚动，步骤完成后折叠|
|Onyx Deep Research|深度研究步骤列表|展开|可折叠，展示检索到的文档|
|ChatGPT / DeepSeek R1|完整思考链文本（灰色 / 折叠）|可折叠|点击展开 / 收起，流式输出|
|RagFlow|不展示推理过程|隐藏|仅展示最终回答 \+ 引用|
|NotebookLM|不展示推理，只展示来源|隐藏|来源直接标注在回答中|

**洞察**：

- **搜索类步骤**适合展示（用户理解 "在找资料"），降低等待焦虑

- **纯 LLM 思考链**建议默认折叠，因为大部分用户不关心推理过程，只看结论

- 可折叠面板是最优解 —— 好奇的用户能展开，普通用户不受干扰，与你们现有设计方向一致

---

### c\) 引用和来源标注对比

|产品|标注形式|交互方式|点击后行为|
|---|---|---|---|
|RagFlow|行内角标 \[1\]\[2\]|hover 浮卡预览|打开原文抽屉看上下文|
|Perplexity|行内小角标 \+ 底部来源卡片|hover 显示标题|应用内打开原网页|
|NotebookLM|行内 "来源：XX 第 N 页"|点击跳转|左侧定位到对应文档|
|Onyx|引用徽章 \+ 来源列表|点击展开|跳转到源文档|
|行业最佳实践|脚注式编号 \+ 悬浮预览|hover 看片段|点击跳转全文|

**洞察**：**三层引用设计**是行业共识的最优解：

1. **第一层**：正文角标（不干扰阅读）

2. **第二层**：悬浮预览卡片（快速验证，不用跳转）

3. **第三层**：跳转原文 / 抽屉（深度查看上下文）

纯静态前端完全可以实现 —— 角标用 `<sup>` 标签，浮卡用 CSS `:hover` \+ 绝对定位，抽屉用 JS 控制 class 切换。

### d\) 搜索与问答的关系对比

|产品|入口形态|切换方式|结果展示|
|---|---|---|---|
|Perplexity|统一入口，搜索 = 问答|无切换，天然一体|回答 \+ 来源列表|
|Onyx|统一输入框，模式切换|输入栏左侧按钮切换 Chat/Search|Chat 模式：对话；Search 模式：文档列表|
|RagFlow|聊天为主|无独立搜索入口|回答内嵌引用|
|NotebookLM|聊天为主|无独立搜索|左侧 Sources 栏手动浏览|
|Notion AI|搜索栏即问答入口|输入问题自动 AI 回答|回答 \+ 页面链接 \+ 传统搜索结果混合|

**洞察**：

- 对于知识库产品，**搜索和问答不应该是两个割裂的功能**

- 最优范式：**一个输入框 \+ 两种结果展示**—— 输入关键词时展示搜索结果列表，输入自然语言问题时生成 AI 回答 \+ 引用

- 你们已有 `/api/v1/search` 端点，可以在 lite 页增加搜索 Tab 或输入时的智能切换

### e\) 移动端适配对比

|产品|响应式策略|侧边栏处理|输入框位置|
|---|---|---|---|
|Perplexity|移动优先设计|汉堡菜单，抽屉式滑出|底部固定|
|Onyx Widget|移动端全屏模式|无侧边栏，简化界面|底部固定|
|NotebookLM|三栏变单栏，Tab 切换|底部 Tab 导航|底部固定|
|RagFlow|支持响应式|汉堡菜单折叠|底部固定|
|AnythingLLM|桌面端为主，Web 端自适应|可折叠侧边栏|底部|

**洞察**：

- 移动端**输入框固定在底部**是标配，符合手机输入法交互

- 侧边栏一律改为**汉堡菜单 \+ 抽屉**，纯 CSS transform 即可实现

- 多栏布局在窄屏下改为**Tab 切换**（如 NotebookLM 的三栏变三 Tab），实现成本低

## 三、Top 3 最值得借鉴的设计模式

### 🥇 第一名：三层引用交互体系（角标 \+ 悬浮预览 \+ 原文抽屉）

**来源参考**：RagFlow \+ 行业通用最佳实践

**设计描述**：

1. **行内角标**：回答中用 `[1]` `[2]` 上标标注，不打断阅读流

2. **悬浮预览卡**：鼠标悬停角标时弹出小卡片，显示文档标题 \+ 原文片段 \+ 置信度

3. **原文抽屉**：点击角标从右侧滑出抽屉，展示完整原文段落及上下文

**为什么适配你们的技术约束**：

- ✅ **纯静态前端可实现**：角标用 `<sup>`，悬浮用 CSS `:hover`，抽屉用 JS 切换 class，不需要 React/Vue

- ✅ **后端零额外成本**：RAG 检索结果本身就带文档片段，直接传给前端渲染即可

- ✅ **单进程无压力**：所有交互都在浏览器端完成，不增加后端请求

- ✅ **知识库问答核心价值**：引用是 RAG 产品的信任基石，比 "聊天体验" 更重要

**实现建议**：先做角标 \+ 底部来源列表（最简版），再迭代悬浮预览（中级），最后加抽屉（高级）。

---

### 🥈 第二名：Workspace（工作区）容器化信息架构

**来源参考**：AnythingLLM \+ NotebookLM \+ Perplexity Spaces

**设计描述**：

- 以 "工作区" 为顶层组织单元，每个工作区包含：文档集合 \+ 对话历史 \+ 独立设置

- 左侧边栏展示工作区列表，点击切换整个上下文

- 新建工作区 = 新建知识库项目，引导用户先建库再聊天

**为什么适配你们的技术约束**：

- ✅ **信息架构清晰**：解决 "选项目→进入聊天" 的割裂感，用户心智模型明确

- ✅ **纯静态可实现**：侧边栏 \+ 主区域的经典布局，原生 JS 切换内容即可

- ✅ **后端天然匹配**：你们的 wiki 目录标记本身就是按目录组织的，一个目录对应一个 Workspace

- ✅ **小团队场景适配**：家庭 / 小团队使用不需要复杂的权限体系，工作区隔离足够

**对现有设计的改进**：把 "项目卡片选择页" 融入侧边栏，进入应用直接显示最近使用的工作区聊天页，省略单独的选择页步骤。

---

### 🥉 第三名：统一输入框 \+ 搜索 / 问答智能切换

**来源参考**：Perplexity \+ Onyx \+ Notion AI

**设计描述**：

- 页面只有一个主输入框，不区分 "搜索" 和 "聊天"

- 输入短关键词（\< 5 字 / 无疑问词）→ 展示搜索结果列表

- 输入自然语言问题（含 "什么"" 怎么 ""为什么" 等）→ 生成 AI 回答 \+ 引用

- 输入框旁可手动切换模式，覆盖自动判断不准的场景

**为什么适配你们的技术约束**：

- ✅ **复用现有 API**：你们已有 `/api/v1/search` 和问答接口，前端只做路由分发

- ✅ **减少页面跳转**：一个入口完成两种任务，降低认知负担

- ✅ **纯 JS 逻辑判断**：前端根据输入内容特征决定调用哪个接口，无需框架支持

- ✅ **符合知识库使用习惯**：用户有时想 "找文档"，有时想 "问问题"，两种需求交替出现

**实现建议**：第一阶段可以先做 "两个 Tab 切换"（搜索 Tab \+ 聊天 Tab），第二阶段再做智能判断的统一入口。

## 五、总结建议

基于你们 "纯 HTML \+ 原生 JS \+ Rust 后端 \+ 单进程自部署 \+ 小团队使用" 的约束，**优先级建议**：

1. **立即优化**：引用系统升级为角标 \+ 底部来源列表（成本最低，价值最高）

2. **下个版本**：Workspace 信息架构改造，去掉单独的项目选择页，改为侧边栏直接切换

3. **后续迭代**：统一搜索 / 问答入口 \+ 增加搜索结果页面

4. **体验打磨**：深色模式、移动端适配、快捷键

这些改进都可以在不引入前端框架、不增加后端复杂度的前提下完成，完全匹配你们的技术栈约束。
