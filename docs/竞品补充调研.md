知识库 AI 问答产品 - 竞品调研补充报告（第 2 轮）
补充一：缺漏的竞品分析
1. Dify
一句话定位：开源 AI 应用开发平台，以可视化工作流编排为核心，对话界面支持知识库检索引用与工作流步骤展示。
界面布局描述：
双模式切换：「工作室」（工作流编排视图）与「对话」（用户使用视图），顶部 Tab 切换
对话页：左侧会话列表 + 中央聊天区 + 右侧可展开的调试面板（工作流节点日志）
知识库引用：回答下方展示引用段落卡片，包含原文片段、分段编号、匹配度百分比
Chunk 预览页：知识库管理中，每个文档以列表形式展示分块，默认只显示前两行，可展开查看完整内容，每页 10 个分块
值得借鉴的设计点：
引用卡片底部聚合：回答正文保持干净，所有引用以卡片形式集中在消息底部，展示原文片段 + 匹配度 + 跳转链接，用户可一键验证
Chunk 列表管理界面：分页列表 + 默认折叠 + 展开查看的模式，适合管理员检查文档分块质量，纯表格布局即可实现
工作流节点日志侧边栏：右侧抽屉展示每个节点的执行状态和输入输出，对调试 RAG 链路非常有价值
2. Sourcegraph Cody
一句话定位：代码库 AI 助手，以 @-mention 方式精确引用文件 / 符号，回答中行内标注代码来源。
界面布局描述：
聊天面板位于侧边栏，输入框支持 @ 唤起上下文选择菜单（文件、文件夹、符号、仓库）
选中的上下文以「芯片（chip）」形式显示在输入框上方，可单独移除
回答中的代码引用：行内标注文件名 + 行号范围，点击跳转到对应代码位置
自动包含当前打开文件和仓库作为上下文，用户无需手动添加
值得借鉴的设计点：
@-mention 上下文选择器：输入时打 @ 弹出文件搜索菜单，选中后以 chip 形式展示，直观可控，纯 JS 可实现
上下文芯片（Context Chips）：输入框上方展示已选文件，每个 chip 带删除按钮，让用户清晰知道 "AI 看了哪些资料"
自动上下文 + 手动补充：默认注入当前环境上下文（当前工作区文档），同时允许用户手动 @ 添加，兼顾便利与精准
3. Cursor / Zed AI
一句话定位：AI 原生代码编辑器，对话面板深度集成代码上下文，支持文件级和代码块级引用。
界面布局描述：
侧边 AI 面板，通过快捷键 ⌘L 唤起，包含聊天输入、模型选择、历史记录
输入框支持 @ 引用文件 / 文件夹 / 符号 / 历史对话，弹出下拉选择菜单
回答中引用的代码：以独立代码块展示，顶部标注来源文件路径，点击跳转
Agent 模式下展示思考步骤和工具调用过程
值得借鉴的设计点：
轻量级文件引用 chip：文件名 + 小图标 + 删除按钮的标签式设计，占用空间小，信息清晰，纯 CSS 即可实现
代码片段独立展示：回答中引用的文档 / 代码片段用独立容器包裹，带标题栏（来源路径），与正文区分明显
快捷键驱动：所有核心操作都有快捷键（打开聊天、新建对话、切换模式），高频用户效率极高
4. 中文产品（Kimi / 豆包知识库）
一句话定位：国产大模型对话产品，支持文件上传 / 知识库问答，引用展示符合中文用户习惯。
界面布局描述：
Kimi：
对话气泡无边框设计，内容直接展示在背景上
联网搜索 / 知识库回答带数字脚注 [1][2]，鼠标悬浮弹出原文预览卡片
深色模式叫「月之暗面」，浅色叫「月之亮面」
文件拖拽上传，支持长文档解析，段落精准引用
豆包：
上下结构布局，上方智能体选择，中央对话区，底部输入框
输入框右侧集成语音、图片、文件等扩展功能
知识库问答支持引用角标，火山引擎方舟版支持来源标注
侧边栏半屏导航，对话列表收纳在左侧
值得借鉴的设计点：
悬浮预览脚注：Kimi 的脚注 + hover 预览模式是中文产品里体验最好的，与国际最佳实践一致
无边框气泡设计：去掉消息气泡边框，直接在背景上展示内容，视觉更轻盈，阅读干扰更少
输入框多功能集成：语音、图片、文件、智能体切换都集中在输入框周边，操作路径短
补充二：搜索结果页面的交互设计
竞品搜索结果页分析
Perplexity 搜索结果
双栏布局：左侧回答区（问题 + AI 回答 + 内联引用角标），右侧固定 Sources 面板
来源卡片：每个来源是一张小卡片，包含 favicon、域名、截断标题，横向排列或纵向列表
回答内联引用：正文中的 [1] 角标与右侧来源卡片联动，hover 时高亮对应来源
设计理念：回答与来源同屏可见，用户读一句话就能瞟到来源，验证成本极低
传统搜索引擎（Google / 百度）
列表式布局：每条结果 = 标题（蓝色可点击）+ 摘要（两行截断，约 160 字符）+ URL 路径
关键词高亮：摘要中匹配的搜索词用 <b> 或 <mark> 加粗 / 高亮
分页 / 无限滚动：传统分页为主，移动端更多无限滚动
可复用模式：
✅ 关键词高亮（<mark> 标签）
✅ 摘要截断（围绕关键词的上下文窗口，而非固定字数）
✅ 标题 + 摘要 + 元信息的三段式结构
Dify 知识库搜索
Chunk 片段展示：搜索结果直接展示匹配的文本分块，不是整篇文档
匹配度分数：每个结果带相似度百分比
跳转原文：点击跳转到知识库分块详情页
关键词高亮：检索词在片段中高亮显示
知识库搜索结果页设计建议
1. 整体布局：列表式（优于卡片式）
理由：知识库搜索是效率工具，列表信息密度更高，扫描速度更快。卡片适合图片丰富的电商 / 内容搜索，文档搜索用列表更合适。
HTML 结构：
html
预览
<div class="search-results">
  <!-- 每个结果项 -->
  <div class="search-result-item">
    <div class="result-title">
      <a href="/doc/xxx">项目部署手册 v2.1</a>
    </div>
    <div class="result-snippet">
      ...在服务器上执行 <mark>docker-compose up</mark> 启动服务，
      配置文件位于 config/env.yaml 中，需要修改数据库连接...
    </div>
    <div class="result-meta">
      <span class="meta-filename">部署手册.md</span>
      <span class="meta-path">/docs/运维/</span>
      <span class="meta-time">更新于 2 天前</span>
      <span class="meta-score">匹配度 87%</span>
    </div>
  </div>
</div>
2. 摘要截断策略
不固定字数，采用关键词上下文窗口：以搜索词为中心，前后各取 60-80 字，确保用户能看到关键词所在的语境
截断标记：前后用省略号 ... 表示有更多内容
单条摘要长度：控制在 120-200 字之间，两行左右
3. 关键词高亮
使用 <mark> 标签实现，语义正确，浏览器原生支持
CSS 自定义高亮颜色，与主题色统一：
css
mark {
  background-color: var(--highlight-bg);
  color: var(--highlight-text);
  padding: 0 2px;
  border-radius: 2px;
}

表格
元信息	必要性	说明
文档标题	必须	点击跳转原文
高亮摘要	必须	展示匹配上下文
文件名	必须	对应物理文件

5. 搜索与问答的切换入口
在搜索框右侧放一个切换按钮：🔍 搜索 / 💬 问答
或者输入时智能判断：短词（<5 字）默认展示搜索结果，完整句子默认走问答
两种结果都保留切换入口，允许用户反悔

定位策略
桌面端：绝对定位在角标右下方，通过 JS 计算角标的 getBoundingClientRect() 设置 top 和 left
防溢出检测：如果右侧空间不足 320px，改为在角标左上方弹出
移动端：没有 hover，改为点击角标显示 / 隐藏卡片，点击空白处关闭
显示 / 隐藏逻辑
桌面：mouseenter 显示，mouseleave 延迟 200ms 隐藏（给用户移到卡片上的时间）
移动端：点击切换显示状态
卡片内的内容可以滚动，pointer-events 设为 auto

补充五：Dify 工作流步骤式进度展示
Dify 的实现原理
SSE 事件驱动
Dify 的工作流对话使用基于 SSE（Server-Sent Events）的流式事件，每个节点执行状态通过独立事件推送：
表格
事件类型	触发时机	携带数据
workflow_started	工作流开始执行	工作流 ID、节点总数
node_started	某个节点开始执行	节点 ID、节点名称、节点类型
node_finished	某个节点执行完成	节点 ID、执行耗时、输出数据摘要
workflow_finished	整个工作流完成	最终结果、总耗时
message	文本内容流式输出	增量文本 token
前端展示逻辑
收到 node_started → 在步骤列表中添加一个「进行中」状态的步骤项
收到 node_finished → 将对应步骤状态改为「已完成」，显示耗时
收到 message → 在最终回答区域流式追加文本
右侧可展开的「工作流日志」面板展示每个节点的详细输入输出
适配我们场景的方案：RAG 三步进度
对于知识库问答场景，不需要完整的工作流编排，只需要展示 RAG 的三个核心步骤即可，比单纯的 "思考中" 更有信息量：
plaintext
🔍 正在检索知识库...  ✅
🤔 正在生成回答...    ⏳
📝 整理引用来源...    ⏳
为什么比 reasoning panel 更好
用户可理解：「检索 → 生成 → 整理」三步用户一看就懂，比抽象的 "思考过程" 更具象
进度感知：每完成一步打一个勾，用户知道 "已经进展到哪了"，减少等待焦虑
技术简单：不需要解析 <think> 标签，后端在三个阶段分别发事件即可
不占空间：步骤条横向排列或紧凑纵向列表，比大段推理文本更省屏幕

最终：前端 UI 设计决策清单
以下是一组可以直接落地实现的设计决策，全部兼容「纯 HTML + 原生 JS + 无框架 + 单进程自部署」约束：
1. 引用系统
角标形式：使用 <sup class="citation-badge"> 上标 + 背景色
悬浮预览：JS 计算定位，绝对定位卡片，桌面 hover 显示、移动端点击显示
底部汇总：回答底部用 CSS Grid 展示来源卡片列表，编号与正文角标对应
跳转原文：点击跳转到文档详情页，带锚点定位
2. 深色模式
实现方案：CSS 变量 + data-theme 属性切换
变量数量：至少 12 个变量（背景 3 层 + 文字 3 层 + 边框 2 层 + 强调色 2 个 + 气泡 2 套）
持久化：localStorage 保存用户选择，默认跟随系统
3. 搜索结果页
布局：垂直列表，每条 = 标题 + 高亮摘要 + 元信息行
高亮：<mark> 标签 + CSS 自定义颜色
摘要策略：关键词为中心的上下文窗口（前后各 60 字），前后省略号
元信息：文件名、路径、更新时间（必选）；匹配度（可选）
4. 空状态设计
三级空状态：落地页 → 全局无工作区 → 工作区内无对话
推荐问题：工作区有文档时，展示 3-4 个上下文相关的推荐问题，点击直接发送
核心 CTA：无文档时引导上传 / 导入，有文档时引导提问
5. Workspace 侧边栏
结构：顶部 Logo + 新建 → 中间工作区列表 → 底部设置 + 用户
当前项高亮：左侧竖条 + 背景加深
移动端：汉堡菜单 + 抽屉滑入 + 遮罩层
文档数徽章：每个工作区显示文档数量，帮助用户判断内容丰富度
6. RAG 步骤进度
三步展示：检索知识库 → 生成回答 → 整理引用
状态标识：进行中（动画）、已完成（打勾）、待执行（灰色）
完成后折叠：生成结束后收起为一行摘要（基于 N 篇文档・耗时 Xs）
替代方案：可与现有 reasoning panel 并存，步骤条显示外层流程，折叠面板显示详细推理
7. 输入框设计
位置：底部固定，移动端跟随输入法弹起
扩展功能：文件上传、模式切换（搜索 / 问答）放在输入框右侧
上下文 chips：如果支持手动选择文档，输入框上方展示已选文件 chip
快捷键：Enter 发送，Shift+Enter 换行，⌘K 聚焦搜索框
