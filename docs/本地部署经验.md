# 本地部署经验总结

> 最后更新：2026-07-18
> 适用：首次在开发机上从零启动 `llm-wiki-server`

---

## 1. 构建耗时与依赖

### 1.1 编译时间 ~11 分钟

```text
Finished release profile in 11m 07s
```

**原因：** `lancedb` 及其依赖链（arrow / datafusion / prost-build）包含大量编译单元，第一次构建需要下载 + 编译数百个 crate。

**改善建议：**

| 场景 | 做法 |
|------|------|
| 日常调试 | `cargo build`（debug 模式，更快）而非 `--release` |
| 修改小代码段 | `cargo check` 只检查编译，不产生二进制 |
| 首次 CI | 缓存 `target/` 目录 |
| 需要生产性能 | 保留 `--release`，提前预留 10-15 分钟 |

### 1.2 protoc 缺失

```text
Error: Custom { kind: NotFound, error: "Could not find `protoc`..." }
```

`lancedb` 通过 `prost-build` 编译 `.proto` 文件，需要 `protoc` 编译器在 PATH 中。

**修复：** 项目已自带 `protoc`，通过环境变量指定：

```bash
export PROTOC=/home/li/overseas-github/llm_wiki-server/.tools/protoc/bin/protoc
```

或写入 `~/.bashrc` 持久化：

```bash
export PROTOC=$HOME/overseas-github/llm_wiki-server/.tools/protoc/bin/protoc
```

> 此问题已在文档和 CLAUDE.md 中记录，但 `protoc` 仍需手动设置环境变量，容易忘记。建议在 `build-all.sh` 或 `build-cli.sh` 中自动检测并设置。

## 2. 构建命令的工作目录

仓库 **没有** 根级 `Cargo.toml` workspace，工作空间分散在 `overlay/server/` 和 `overlay/auth/` 等子目录中。

| 命令 | 正确用法 |
|------|---------|
| **编译 server** | `cd overlay/server && cargo build --release` |
| **检查 server** | `cd overlay/server && cargo check` |
| **运行 auth 测试** | `cd overlay/auth && cargo test` |

~~`cargo build -p llm-wiki-server` 从根目录运行会报错~~（找不到 Cargo.toml）。

## 3. 路径别名踩坑

启动脚本中，用 **连字符** `llm_wiki-server` 而非 `llm_wiki_server`：

```bash
# ❌ 错误
export LLM_WIKI_CONFIG=/home/li/overseas-github/llm_wiki_server/overlay/config/...

# ✅ 正确
export LLM_WIKI_CONFIG=/home/li/overseas-github/llm_wiki-server/overlay/config/...
```

这种混淆可能在 `Tab` 补全时不显现，建议始终用仓库真实路径。

## 4. API 访问注意事项

### 4.1 项目 ID 解析

`/api/v1/projects` 返回项目列表时带 UUID。**不能用项目名作为 project_id**：

```bash
# ❌ 失败: Unknown project
curl ... /api/v1/projects/ParentingBooks/search

# ✅ 成功：用 current 别名
curl ... /api/v1/projects/current/search

# ✅ 成功：用 UUID
curl ... /api/v1/projects/a8f3c2e1-.../search
```

### 4.2 Auth 路由前缀

认证路由挂在 **`/auth/`** 而非 `/api/v1/auth/`：

```bash
# ✅ 正确
curl -X POST http://127.0.0.1:8080/auth/register

# ❌ 会返回 401（因为走了 Bearer 鉴权）
curl -X POST http://127.0.0.1:8080/api/v1/auth/register
```

### 4.3 注册不需要 Bearer token

注册和登录是**公开的**（除非 `LLM_WIKI_DISABLE_REGISTRATION=true`），不需要 `Authorization` 头：

```bash
# 注册
curl -X POST -H "Content-Type: application/json" \
  -d '{"email":"a@b.com","password":"Abc12345!"}' \
  http://127.0.0.1:8080/auth/register

# 登录（获取 session cookie）
curl -c cookies.txt -X POST -H "Content-Type: application/json" \
  -d '{"email":"a@b.com","password":"Abc12345!"}' \
  http://127.0.0.1:8080/auth/login

# 用 cookie 访问
curl -b cookies.txt http://127.0.0.1:8080/auth/me
```

## 6. `authDb: null` 错觉

健康检查返回的 `authDb: null` **不代表 auth 没有启用**。只要设置了 `LLM_WIKI_AUTH_DB` 环境变量指向有效的 SQLite 路径，auth 就正常工作。

```json
{
  "authDb": null,           ← 此字段只是健康检查不暴露路径（安全考虑）
  "authRequired": true,     ← 关键看这里
  "authConfigured": true    ← 以及这里
}
```

实际验证 auth 是否工作：直接访问 `/auth/register` 看是否返回 200。

## 7. `setsid` & 后台进程行为

用 `setsid` + `&` 启动时：

```bash
setsid ./llm-wiki-server > /tmp/server.log 2>&1 &
```

- shell 会立即输出 `[1]+ Done`，**这不代表 server 挂了**
- `setsid` 为子进程创建新 session 然后自己退出，shell 报告的是 `setsid` 命令完成
- 真正的 server 进程仍在后台运行（用 `ps aux | grep llm-wiki-server` 确认）

推荐用 `nohup` 或 tmux 替代 `setsid` 以便管理：

```bash
nohup ./llm-wiki-server > /tmp/server.log 2>&1 &
```
